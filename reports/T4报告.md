# YOLO11n 在 Tesla T4 上的推理基准测试报告

本实验对 COCO 预训练 YOLO11n 进行精度验证与同步推理测试。TensorRT FP16 与 TensorRT FP32 的 mAP50-95 绝对差约为 **0.00000929，即 0.000929 个百分点**。性能按三轮算术平均汇总：TensorRT FP16 Batch 1 吞吐为 165.45 img/s，FP32 为 135.24 img/s，吞吐比约 **1.22 倍**；已测配置中静态 FP16 Batch 4 推理吞吐最高，为 **273.15 img/s**。

这些数值适用于当前模型、固定图片批次、640×640 输入和同步 Python pipeline。Batch 8 吞吐下降是实测现象，具体原因仍需 profiling 验证。

## 1. 数据来源与计算方法

| 指标 | 来源或计算方式 |
| --- | --- |
| mAP、Precision、Recall、各类别 AP | Ultralytics model.val() 计算，项目读取并保存 |
| 单次前处理、后端调用、后处理、E2E 耗时 | 项目通过 time.perf_counter() 计时 |
| 单轮均值、标准差 | statistics.fmean()、statistics.pstdev() |
| 单轮 P50/P95/P99 | numpy.percentile()，默认线性插值 |
| 单轮推理吞吐 | batch × 1000 / 单轮平均推理毫秒 |
| 三轮汇总 | 三个单轮结果的算术平均；跨轮标准差使用总体标准差 |
| GPU 利用率、显存、功耗、温度、频率 | nvidia-smi 每 200 ms 采样，按 GPU index 汇总 |

计算实现见 [benchmark.py](../yolo_benchmark/benchmark.py)、[validation.py](../yolo_benchmark/validation.py)、[gpu_monitor.py](../yolo_benchmark/gpu_monitor.py) 和 [汇总脚本](../scripts/generate_nvidia_report.py)。

精度来源为 results/t4/val2017 下的 pt_fp32.json、trt_fp32_b1.json 和 trt_fp16_b1.json。性能仅使用 results/t4/t4_matrix_val2017 下的 30 个 repeat JSON，与该目录 [summary.md](../results/t4/t4_matrix_val2017/summary.md) 的 Repeat Aggregate 对齐。早期 t4_matrix_official 和另一轮 validation 结果不混入本表。

实验比较 PyTorch、ONNX Runtime CUDA、TensorRT，以及 FP32/FP16、静态/动态 Batch 1/4/8 的性能和精度取舍。INT8 未纳入本轮实测，本报告不提供其加速预测。

| 项目 | 存档配置 |
| --- | --- |
| GPU | Tesla T4，compute capability 7.5 |
| 总显存 | 环境 JSON 记录为 15360 MiB；空闲显存随运行状态变化 |
| 功耗上限 | 70 W |
| Driver | 580.178.04 |
| TensorRT | 11.5.0.63 |
| PyTorch / CUDA runtime | 2.11.0+cu130 / 13.0 |
| Ultralytics / ONNX Runtime | 8.4.219 / 1.30.0 |
| Python | 3.13.16 |
| 平台 | Kaggle Notebook，目标设备 GPU 0 |

以上版本和硬件标识来自结果 JSON。T4 不支持 TF32，但具体算子的执行精度、kernel 和 tactic 仍需查看构建信息或 profiler，不能仅根据 FP32 标签推导全部执行细节。

## 3. 制品与精度验证方法

T4 构建脚本以 yolo11n.pt 为源，输入尺寸 640，动态构建 batch 参数为 8，workspace 参数为 4 GiB，生成 ONNX 和独立命名的 TensorRT Engine。动态 Engine 的实际范围以 profile 为准；本次已测 Batch 1/4/8。

| 验证制品 | JSON 记录字节数 | 十进制 MB |
| --- | ---: | ---: |
| yolo11n.pt | 5,613,764 | 5.61 |
| TensorRT FP32 b1 | 167,059,086 | 167.06 |
| TensorRT FP16 b1 | 67,387,716 | 67.39 |

大小来自 model.size_bytes，MB 按 bytes / 1,000,000 计算。JSON 同时保存模型 SHA256 和本地 dataset YAML SHA256。构建耗时、逐层精度和编译阶段占比未由这些 JSON 给出，不作为本报告已核实数值列出。

Engine 应在目标硬件和兼容软件栈中构建并验收。若日志出现共享常量复制或小权重钳位，需通过精度回归验证影响，不能直接断言对模型行为没有影响。

精度验证使用实验记录中的 COCO val2017 全量集。三个验证 JSON 指向相同的本地 dataset YAML，split 为 val、imgsz 为 640、batch 为 1。mAP50-95 在 IoU 0.50～0.95、步长 0.05 的十档及类别间取平均，由 Ultralytics 实现。

相同 imgsz 参数不保证不同后端的 padding、实际输入形状和后处理路径完全相同。因此 PyTorch 与 TensorRT 的差值包含完整部署链路差异；TensorRT FP32 与 FP16 的对照更接近隔离精度转换影响。

## 4. 性能测量口径

每个配置 warmup 50 次，正式测量 500 次，独立执行三轮。GPU monitor 在 warmup 后启动，正式测量结束或抛异常时停止。

**实际图片使用方式：**当前 CLI 只调用一次 load_images(source, batch, size)，从目录按文件名排序选出 batch 张图片，然后反复使用这一批。即使目录包含 1000 张图片，Batch 1/4/8 分别只使用固定的 1/4/8 张，500 次迭代不会遍历整个目录。这是固定批次微基准；不同 batch 的图片内容和检测框数量也可能影响后处理耗时。

计时边界如下：

- 前处理：CPU letterbox、颜色转换、归一化和 batch 构建；不包含磁盘读图。
- inference：同步边界内的后端调用，包含后端内部输入拷贝、转换、执行、同步和输出回到 CPU。
- 后处理：CPU 输出解码、置信度过滤、NMS 和坐标还原。
- E2E：一轮前处理开始到后处理结束，包含阶段间开销；不包含模型加载和网络服务。

inference 是主机可观察后端耗时，不是纯 GPU kernel 时间。验证 JSON 的 speed_ms_per_image 来自 Ultralytics 的另一条执行和计时路径，不能与本矩阵混用。

三轮汇总定义：

```text
报告推理均值 = mean(各轮 inference_mean_ms)
报告吞吐     = mean(各轮 batch × 1000 / inference_mean_ms)
报告 P95     = mean(各轮 inference_p95_ms)
跨轮 CV      = pstdev(各轮 inference_mean_ms) / mean(...) × 100%
摊销 ms/图   = 报告推理均值 / batch
```

平均吞吐不严格等于 batch × 1000 / 报告推理均值，因为倒数与取平均不能交换。P95 列是三轮 P95 的平均值，不是合并 1500 个样本后的 P95。

跨轮推理 CV 范围约 0.28%～3.25%。TensorRT FP32 三轮推理均值的相对极差约为 7.77%，原文“三轮极差全部低于 5%”不成立。这些统计也不能单独证明 GPU 频率稳定。

## 5. 精度结果

分数以 0～1 表示；相对变化列用百分制百分点。

| 模型 | mAP50-95 | mAP50 | Precision | Recall | 相对 PyTorch mAP50-95 |
| --- | ---: | ---: | ---: | ---: | ---: |
| PyTorch FP32 | 0.389863 | 0.545828 | 0.651873 | 0.504568 | 基准 |
| TensorRT FP32 b1 | 0.388900 | 0.544659 | 0.649389 | 0.498344 | −0.0964 个百分点 |
| TensorRT FP16 b1 | 0.388890 | 0.544606 | 0.646832 | 0.500063 | −0.0973 个百分点 |

TensorRT FP32 与 FP16 的差值：

```text
0.388899707325095 − 0.3888904212161857
= 0.0000092861089093（0～1 分数）
= 0.00092861089093 个百分点（百分制）
```

本验证集上两者总体 mAP 非常接近，但不能称为所有类别、所有图片输出完全一致，也不能无条件推导已满足业务上线标准。

类别 AP 存在细微差异。FP16 的 handbag、book、spoon AP 分别约为 0.0882、0.1032、0.1080；hair drier 约为 0.000268，接近零但不是零。结构化结果未保存该类别实例数和完整召回明细，不能仅凭 AP 接近零就断言召回为零或给出确定原因。

官方标称值与本地结果若有差异，应核对权重、数据、输入形状、验证参数和工具版本，未经受控对照不能确定归因为 padding 或版本差异。

## 6. 性能结果

下表均为三轮算术平均。推理均值、P95 和 E2E 单位为每批毫秒；摊销 ms/图不等于批内单张图片的完成延迟。

| 配置 | 推理均值 ms/批 | P95 均值 ms/批 | 推理吞吐 img/s | 摊销 ms/图 | E2E 均值 ms/批 | 跨轮推理 CV |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| PyTorch FP32 b1 | 12.73 | 14.66 | 78.53 | 12.73 | 21.31 | 0.67% |
| PyTorch FP16 b1 | 15.65 | 17.44 | 63.91 | 15.65 | 24.33 | 1.24% |
| ONNX Runtime CUDA b1 | 7.56 | 7.88 | 132.32 | 7.56 | 16.37 | 1.25% |
| TensorRT FP32 b1 | 7.40 | 8.80 | 135.24 | 7.40 | 15.80 | 3.25% |
| TensorRT FP16 b1 | 6.05 | 6.96 | 165.45 | 6.05 | 14.62 | 1.60% |
| TensorRT FP16 b4 | 14.64 | 15.01 | 273.15 | 3.66 | 41.87 | 0.30% |
| TensorRT FP16 b8 | 33.81 | 39.37 | 236.62 | 4.23 | 100.04 | 0.48% |
| 动态 FP16 b1 | 5.86 | 6.14 | 170.66 | 5.86 | 12.72 | 1.98% |
| 动态 FP16 b4 | 15.16 | 15.54 | 263.85 | 3.79 | 43.35 | 0.28% |
| 动态 FP16 b8 | 32.19 | 39.63 | 248.51 | 4.02 | 95.12 | 0.52% |

### 6.1 Batch 与精度取舍

静态 FP16 b4 的推理吞吐为 273.15 img/s，相对 PyTorch FP32 b1 为约 3.48 倍。这个对比同时改变后端、精度和 batch，表示整体配置收益。

静态 FP16 从 b4 增至 b8，推理吞吐下降约 13.37%，摊销耗时从 3.66 升至 4.23 ms/图，P95 从 15.01 升至 39.37 ms/批。P95 比较也包含批次工作量翻倍，不能直接说单图尾延迟增加相同比例。

TensorRT b1 的 FP16/FP32 推理吞吐比约为 1.22。PyTorch FP16 在本配置下慢于 FP32，仍是应保留的实测结果；其原因需检查 kernel 选择、转换和框架开销，不能仅凭未使用 TensorRT 就确定归因。

### 6.2 动态与静态引擎

动态引擎在 b1、b8 的吞吐高于对应静态引擎，但 b4 为 263.85 img/s，比静态的 273.15 img/s 约低 3.40%。本轮支持动态引擎总体性能接近、覆盖多个已测 batch，不支持“没有性能代价”的普遍结论。

动态 b1 的 E2E 为 12.72 ms，静态为 14.62 ms；平均前处理分别为 2.09 和 3.85 ms。CPU 前处理差异解释了很大一部分 E2E 差距，不能把全部优势归因于动态 Engine。

### 6.3 CPU 前后处理和业务吞吐

| 静态 FP16 | 前处理 ms/批 | 后处理 ms/批 | inference ms/批 | E2E ms/批 |
| --- | ---: | ---: | ---: | ---: |
| b1 | 3.85 | 4.67 | 6.05 | 14.62 |
| b4 | 11.37 | 15.76 | 14.64 | 41.87 |
| b8 | 40.98 | 25.14 | 33.81 | 100.04 |

三段之和与 E2E 之间仍有同步和调用间开销。b8 前处理增长明显，应调查图片尺寸、内存分配和 CPU 调度等因素；后处理还受检测框数量影响。

273.15 img/s 仅按 inference 计时计算。以 b4 平均 E2E 估算，串行同步 pipeline 约为 4 × 1000 / 41.87 ≈ 95.5 img/s；这是派生估算，不包含磁盘读图或网络服务成本。

GPU 功耗采样覆盖正式测量的整个 pipeline。现有 images_per_second_per_watt 为“推理吞吐 / pipeline 平均功耗”的近似比值，不能直接视为纯 kernel 能效或精确单图能耗。

## 7. 异常分析与证据边界

### Batch 8 退化

当前可确认推理吞吐下降、CPU 前后处理耗时增加。潜在原因包括 engine tactic/profile、输入输出传输、内存分配、CPU 调度、后处理工作量和 GPU 时钟变化。

目前没有缓存命中率、实际 DRAM 流量或与单次延迟对齐的降频证据。不能断言“激活超过 L2 导致退化”，也不能仅凭 P95 升高确认触发功耗降频。后续应结合 GPU 时间序列、TensorRT profiler 和 Nsight Systems，再对热点使用 Nsight Compute。

### 算力与访存瓶颈

模型 FLOPs / GPU 峰值算力只是理想化参考。实际 kernel 形状、硬件利用率、launch、同步和传输都影响延迟；FP16 没达到理论峰值比例的加速，不足以排除计算瓶颈。

耗时 × 理论显存带宽不是实测数据搬运量。缺少实际字节数、实际带宽和算术强度，不能据此建立可信的 roofline 归因。本报告不将 workload 定性为“严重访存受限”。

### ONNX Runtime 形状敏感性

本表仅覆盖公共 pipeline 生成的 640×640 输入。实验过程曾记录矩形输入下 cuDNN Frontend 查询失败和异常变慢，但当前矩阵 JSON 不足以确认具体失败路径、回退范围或根因。

不能概括为“ORT 一定整图回退 CPU”。需结合异常栈、Session 设置、provider 日志和节点 profiling 判断；Session 中启用 CUDA EP 也不代表全部节点都在 GPU 执行。矩形输入应另行复现并保存原始证据。

## 8. 部署建议

| 场景 | 当前候选 | 依据和条件 |
| --- | --- | --- |
| 固定批次高吞吐 | 静态 FP16 b4 | 已测推理吞吐最高；批次 E2E 约 41.87 ms，需符合业务时延预算 |
| batch 波动 | 动态 FP16 | 已测 b1/b4/b8；b4 比静态吞吐约低 3.40%，按实际分布取舍 |
| 单批低延迟 | 动态 FP16 b1 | 本轮 inference 5.86 ms、E2E 12.72 ms；前处理差异需复核 |
| 精度与兼容性对照 | FP32 | 保留为回归基线，性能预算允许时仍有使用价值 |
| b8 / PyTorch FP16 | 暂不优先满足本次性能目标 | 本配置下未优于对应较优选项，不推广到其他 workload |

INT8 未实测，不提供固定加速区间。后续用代表性校准集和冻结验证集，同时检查 mAP、类别级退化、吞吐、尾延迟和功耗；验收阈值由业务要求决定。

## 9. 局限与后续工作

- 当前重复固定图片批次，不能代表遍历全数据集、视频流或在线服务性能。
- 三轮重复提供初步稳定性信息，没有置信区间；共享 CPU 和测试顺序可能影响结果。
- validate 使用 Ultralytics 路径，benchmark 使用自定义前后处理；后者需独立输出一致性验证，不能无条件继承验证 mAP。
- 需要通过 CUDA Event 和主机计时分离 H2D、GPU 执行与 D2H，目前纯 kernel 性能未知。
- Batch 8 退化、动态/静态前处理差异和 PyTorch FP16 变慢仍需受控复现。
- INT8、逐层精度和计算/访存瓶颈尚待实测。
- 结论仅覆盖当前 T4、模型、软件栈和计时方式，跨卡比较需明确环境差异。

本次修订基于已有测量文件核对报告，未重跑模型或修改历史 JSON、CSV、summary 和 benchmark 代码。
